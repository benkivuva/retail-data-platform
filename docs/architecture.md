# Architecture

How the Retail Data Platform is structured, why each layer exists, and how
data moves from source to business value.

## Sources

Two source systems feed the platform. They arrive by different mechanisms
and are both loaded as-is into `raw`.

### Synthetic CSVs

Generated by `data/scripts/generate_raw_data.py` to simulate the operational
systems of an online supermarket: orders, order items, payments, deliveries,
inventory snapshots, products, customers, suppliers, and supplier orders.
Loaded by `data/scripts/load_raw_to_bigquery.py` using the `bq load` CLI.

### Ops Google Sheet

A human-edited operations tracker with three tabs, maintained informally by
the operations team:

| Tab | Grain | Loaded to |
|---|---|---|
| Zone Master | one row per delivery zone | `raw.ops_zone_master` |
| Driver Roster | one row per driver-day assignment | `raw.ops_driver_roster` |
| Vehicle Log | one row per service event | `raw.ops_vehicle_log` |

Loaded by `data/scripts/load_sheets_to_bigquery.py` using the `gspread`
library and the same service account used for BigQuery. All columns are
loaded as STRING; cleaning happens in dbt staging, not in the loader.

The sheet is deliberately realistic — mixed-case county spellings, three
date formats in the same column, phone numbers in three formats, free-text
vehicle descriptions, duplicate rows, and blank rows used as section
separators. The full source profile is in `docs/source_assessment.md`.

## Layers

### Raw (`raw` dataset)

Everything from both sources lands here unchanged. Tables are partitioned
by date where the source provides one; otherwise they are plain tables.

- **Materialisation:** Tables
- **Schema:** Autodetected from CSVs; explicit STRING schema for sheets
- **Loaded by:** `bq load` CLI for CSVs; `gspread` + `load_table_from_json`
  for sheets
- **Consumers:** Staging models only

Raw tables are never queried directly by analysts, dashboards, or AI tools.
Everything flows through staging first.

### Staging (`staging` dataset)

One model per source table. Cleans, casts, and renames — no business logic,
no joins across entities beyond simple lookups.

- **Materialisation:** Views (no storage cost, always current)
- **Naming:** `stg_<source>`
- **Tests:** Uniqueness and not-null on primary keys, referential integrity
  from foreign keys back to `stg_*` models

**Warehouse sources**

- `stg_orders`, `stg_order_items`, `stg_payments`, `stg_deliveries`
  (`ZN001` → `Z001` reconciliation applied here so zone IDs join to the
  ops sheet), `stg_inventory_snapshots`, `stg_products`, `stg_customers`,
  `stg_suppliers`, `stg_supplier_orders`

**Ops sheet sources**

- `stg_ops_zone_master` — trims whitespace, standardises county names
  (`nairobi`, `NBO` → `Nairobi`), casts `Active?` to a boolean, and
  deduplicates the source's `Z028` duplicate
- `stg_ops_driver_roster` — parses three date formats, normalises phone
  numbers to E.164, standardises status values, flags rows referencing
  zones not present in the zone master
- `stg_ops_vehicle_log` — normalises registration casing, parses cost
  strings (`KES 15,000`, `15K`, `15000` → NUMERIC), classifies free-text
  descriptions into vehicle types

### Intermediate (`intermediate` dataset)

Business logic that would otherwise be duplicated across multiple marts.
Joins, aggregations, and derived fields live here.

- **Materialisation:** Views
- **Naming:** `int_<purpose>`
- **Models:**
  - `int_order_totals` — order header joined to item totals and gross margin
  - `int_delivery_times` — dispatch and delivery timing, on-time flag
  - `int_inventory_movements` — day-over-day inventory change, stockout flag
  - `int_supplier_lead_times` — actual lead days and fill rate

Intermediate models are not exposed to BI. They exist so marts stay simple.

### Marts (`marts` dataset)

The star schema and the semantic layer. Everything downstream reads from here.

- **Materialisation:** Tables (heavily queried, so we pay storage to save compute)
- **Dimensions:**
  - `dim_customers`, `dim_products`, `dim_suppliers`, `dim_warehouses`,
    `dim_dates` — from warehouse sources
  - `dim_delivery_zones` — enriched from `stg_ops_zone_master`, adds
    `county` and `dispatch_hub`
  - `dim_drivers` — built from `stg_ops_driver_roster`, one row per driver
    with the most recent phone number and assignment counts; uses an
    md5 surrogate key on the normalised name
  - `dim_vehicles` — built from `stg_ops_vehicle_log`, one row per vehicle
    with service history and total maintenance cost
- **Facts:** `fct_orders`, `fct_order_items`, `fct_deliveries`,
  `fct_inventory_snapshots`, `fct_supplier_orders`
- **Semantic layer:** `metrics_daily` — one row per day, every core metric
  defined once
- **Monitoring:** `mon_pipeline_health` — single row capturing current
  warehouse state (freshness, row counts)

The semantic layer is what makes the platform trustworthy. One metric, one
definition, one owner. See `docs/metric_dictionary.md`.

### AI (`ai` dataset)

PII-free, read-only views purpose-built for AI assistants. They mirror the
marts but strip anything sensitive and expose only aggregated data.

- **Materialisation:** Views
- **Models:**
  - `ai_daily_metrics` — daily business metrics
  - `ai_customers_summary` — aggregated customer counts by segment and channel
  - `ai_products_summary` — aggregated product counts and prices by category

The AI assistant (`ai/ask.py`) reads a context document (`ai/context.md`) and
calls a `run_sql` tool. Every query passes an allowlist that permits only
SELECT statements against these three views.

## Serving layers

Everything below reads from `marts` or `ai`. Nothing reads from `raw`,
`staging`, or `intermediate`, and nothing writes.

### Looker Studio (hosted)

A five-page dashboard reading directly from `marts`:

- Operations, Commercial, Finance, Customers
- Pipeline Health (reads `mon_pipeline_health`)

Configured outside the repo. Link recorded in `dashboards/dashboard_link.md`.

### Flask + Plotly Dash (`platform/`)

An owned, code-first BI application:

- **Flask app factory** — `platform/app/__init__.py` builds the app, registers
  blueprints, applies the auth gate, and mounts each Dash dashboard.
- **Dashboards** — one module per page under `platform/app/dashboards/`, each
  mounted on its own URL base (`/dashboards/<name>/`). All share topbar, KPI
  cards, and chart styling via `_shared.py`.
- **Query layer** — `platform/app/queries/bigquery.py` owns every SQL
  statement. Dashboards never construct queries directly. All queries are
  parameterised and 5-minute memoised.
- **Auth** — Flask-Login with a SQLite-backed `users` table. Three roles:
  admin (all pages), analyst (all dashboards), viewer (operations + commercial
  only). `require_login` runs on every request except `/auth/*`, `/health`,
  and `/static/*`.
- **Session hardening** — `SESSION_COOKIE_HTTPONLY`, `SameSite=Lax`, 8-hour
  lifetime, CSRF protection on forms, generic login error messages,
  open-redirect guard on `next=`.
- **AI chat page** — `/ai/chat` calls the same governed assistant as the CLI,
  via a thin service layer (`platform/app/ai/service.py`). Every question
  passes through the same SQL allowlist.
- **Container** — multi-stage `Dockerfile`, non-root `appuser`, gunicorn
  serving `wsgi:app` on port 8080. Secrets (service account key, API keys,
  session secret) are passed at runtime via env vars and read-only volume
  mounts; nothing is baked into the image.

### Gemini AI (governed SQL)

A function-calling assistant available two ways:

- CLI (`ai/ask.py`) — for ad-hoc queries.
- Web page (`/ai/chat` inside the platform) — for stakeholders.

Both share the same `ask()` implementation, the same `ai/context.md` system
prompt, and the same `is_safe_query()` allowlist.

## Orchestration

Dagster orchestrates the pipeline as an asset graph across three groups.

- **ingestion** — `ops_sheets_ingestion` loads the Google Sheet into
  `raw.ops_*`. Runs first in the DAG.
- **dbt** — one Dagster asset per dbt model (via `dagster-dbt`); runs
  `dbt build` (models + tests).
- **quality** — `soda_raw_checks` runs after dbt and scans the raw layer.

- **Daily 6 AM schedule** — `cron_schedule="0 6 * * *"`
- **Per-asset observability** — status, timing, logs in the Dagster UI
- **Failure guardrails** — a failing dbt test halts downstream models; a
  failing Soda scan fails the pipeline

Entry point: `orchestration/definitions.py`.

## Data quality

Two layers, complementary:

| Layer | Tool | What it covers |
|---|---|---|
| In-warehouse | dbt tests | Primary keys, foreign keys, business rules, metric bounds |
| Raw-layer | Soda Core | Row counts, duplicate IDs, negative values, anomaly thresholds |

A failing dbt test blocks downstream models. A failing Soda check fails the
Dagster run. In CI, a failing test blocks the merge.

Two source-side incidents caught by tests and fixed in staging:

- On-time delivery rate silently reporting 100% (wrong denominator).
- Duplicate `zone_id` in the ops sheet (same zone, two spellings).

Both documented in `docs/data_quality_log.md`.

## Monitoring

Four layers:

- **Dagster UI** — per-asset run history, timing, and error logs
- **Soda Core** — anomaly alerts on the raw layer
- **Looker Studio (Pipeline Health)** — freshness lag, row counts, latest
  metric date, served from `marts.mon_pipeline_health`
- **Platform CI** — pytest + Docker build on every push

## Security and governance

- **PII isolation** — customer names, emails, phones, addresses never leave
  `marts.dim_customers`. AI and dashboards see aggregates only. The ops
  sheet contains driver names and phone numbers, which are internal
  operational data — not customer PII — and are used only in `dim_drivers`.
- **AI allowlist** — the assistant can only SELECT from three PII-free views.
  Non-SELECT statements, multi-statement payloads, and disallowed tables are
  rejected before reaching BigQuery. Covered by unit tests.
- **Role-based access** — three roles gate dashboard visibility.
- **Session hardening** — CSRF, HTTPOnly cookies, SameSite, finite lifetime,
  open-redirect protection.
- **Secrets** — never committed. `.env` for local dev; GitHub Secrets for CI;
  runtime env vars + mounted volumes for the container. The ops sheet is
  shared with the service account as Viewer.

## Cost and performance

- **Views for staging and intermediate** — no storage cost, no stale copies
- **Tables for marts** — expensive joins run once, BI reads the result
- **Aggregation before serving** — `metrics_daily` reduces millions of fact
  rows to one row per day, cutting scanned bytes for dashboards and AI
- **Column selection, never `SELECT *`** — BigQuery costs scale with columns
  read, not rows
- **Response caching** — platform queries are memoised for 5 minutes

See `docs/cost_report.md` for the full breakdown.

## What would change at scale

| Current | Production |
|---|---|
| Synthetic CSV generator + ops Google Sheet | Fivetran, Airbyte, or custom connectors per source system |
| `bq load` CLI + gspread loader | Orchestrated ingestion jobs with retries and alerting |
| Local Dagster dev server | Dagster+ or a scheduled VM |
| SQLite user DB | Postgres or a managed identity provider (SSO) |
| Single-container Flask app | Multiple replicas behind a load balancer (Cloud Run, ECS) |
| Manual dashboard refresh | Scheduled Looker Studio refresh |
| File-based catalogue | DataHub, OpenMetadata, or dbt Cloud catalogue |
| Hand-written AI context | Auto-generated from the dbt manifest |
| Single-project BigQuery | Separate dev, staging, and prod projects |

## Ownership

| Layer | Owner | Change process |
|---|---|---|
| Ingestion scripts (CSV + sheets) | Analytics Engineering | Pull request |
| Staging and intermediate models | Analytics Engineering | PR + tests |
| Marts (dims and facts) | Analytics Engineering + domain owner | PR + tests + owner sign-off |
| `metrics_daily` | Analytics Engineering + metric owner | PR + owner sign-off + change note |
| AI views and assistant | Analytics Engineering | PR + unit tests |
| Flask + Dash platform | Analytics Engineering | PR + pytest + Docker build |
| Ops Google Sheet (source) | Operations | Edit in place; changes flow through next pipeline run |
| Looker Studio dashboards | Domain analysts | PR to dashboard repo |
