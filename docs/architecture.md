# Architecture

How the Retail Data Platform is structured, why each layer exists, and how
data moves from source to business value.

## Layers

### Raw (`raw` dataset)

Source CSVs generated by `data/scripts/generate_raw_data.py` and loaded into
BigQuery by `data/scripts/load_raw_to_bigquery.py`. The data mimics the source
systems of an online supermarket: orders, order items, payments, deliveries,
inventory snapshots, products, customers, suppliers, and supplier orders.

- **Materialisation:** Tables
- **Schema:** Autodetected from CSV headers
- **Loaded by:** `bq load` CLI, orchestrated by Dagster
- **Consumers:** Staging models only

Raw tables are never queried directly by analysts, dashboards, or AI tools.
Everything flows through staging first.

### Staging (`staging` dataset)

One model per source table. Cleans, casts, and renames — no business logic,
no joins.

- **Materialisation:** Views (no storage cost, always current)
- **Naming:** `stg_<source>`
- **Tests:** Uniqueness and not-null on primary keys, referential integrity
  from foreign keys back to `stg_*` models

Example: `stg_orders` renames raw columns, casts `order_date` to DATE, and
`order_timestamp` to TIMESTAMP, but does not compute margin or revenue.

### Intermediate (`intermediate` dataset)

Business logic that would otherwise be duplicated across multiple marts.
Joins, aggregations, and derived fields live here.

- **Materialisation:** Views
- **Naming:** `int_<purpose>`
- **Models:**
  - `int_order_totals` — order header joined to item totals and gross margin
  - `int_delivery_times` — dispatch and delivery timing, on-time flag
  - `int_inventory_movements` — day-over-day inventory change, stockout flag
  - `int_supplier_lead_times` — actual lead days and fill rate

Intermediate models are not exposed to BI. They exist so marts stay simple.

### Marts (`marts` dataset)

The star schema and the semantic layer. Everything downstream reads from here.

- **Materialisation:** Tables (heavily queried, so we pay storage to save compute)
- **Dimensions:** `dim_customers`, `dim_products`, `dim_suppliers`,
  `dim_drivers`, `dim_warehouses`, `dim_delivery_zones`, `dim_dates`
- **Facts:** `fct_orders`, `fct_order_items`, `fct_deliveries`,
  `fct_inventory_snapshots`, `fct_supplier_orders`
- **Semantic layer:** `metrics_daily` — one row per day, every core metric
  defined once
- **Monitoring:** `mon_pipeline_health` — single row capturing current
  warehouse state (freshness, row counts)

The semantic layer is what makes the platform trustworthy. One metric, one
definition, one owner. See `docs/metric_dictionary.md`.

### AI (`ai` dataset)

PII-free, read-only views purpose-built for AI assistants. They mirror the
marts but strip anything sensitive and expose only aggregated data.

- **Materialisation:** Views
- **Models:**
  - `ai_daily_metrics` — daily business metrics
  - `ai_customers_summary` — aggregated customer counts by segment and channel
  - `ai_products_summary` — aggregated product counts and prices by category

The AI assistant (`ai/ask.py`) reads a context document (`ai/context.md`) and
calls a `run_sql` tool. Every query passes an allowlist that permits only
SELECT statements against these three views.

## Orchestration

Dagster orchestrates the pipeline as an asset graph.

- **One asset per dbt model** — the graph mirrors dbt's own DAG
- **Downstream Soda asset** — runs 10 anomaly and validation checks after dbt
- **Daily 6 AM schedule** — `cron_schedule="0 6 * * *"`
- **Per-asset observability** — status, timing, logs in the Dagster UI
- **Failure guardrails** — a failing dbt test halts downstream models; a
  failing Soda scan fails the pipeline

Entry point: `orchestration/definitions.py`.

## Data quality

Two layers, complementary:

| Layer | Tool | What it covers |
|---|---|---|
| In-warehouse | dbt tests | Primary keys, foreign keys, business rules, metric bounds |
| Raw-layer | Soda Core | Row counts, duplicate IDs, negative values, anomaly thresholds |

A failing dbt test blocks downstream models. A failing Soda check fails the
Dagster run. In CI, a failing test blocks the merge.

## Monitoring

Three layers:

- **Dagster UI** — per-asset run history, timing, and error logs
- **Soda Core** — anomaly alerts on the raw layer
- **Looker Studio (Pipeline Health page)** — freshness lag, row counts, latest
  metric date, served from `marts.mon_pipeline_health`

## Cost and performance

- **Views for staging and intermediate** — no storage cost, no stale copies
- **Tables for marts** — expensive joins run once, BI reads the result
- **Aggregation before serving** — `metrics_daily` reduces millions of fact
  rows to one row per day, cutting scanned bytes for dashboards and AI
- **Column selection, never `SELECT *`** — BigQuery costs scale with columns
  read, not rows

See `docs/cost_report.md` for the full breakdown.

## What would change at scale

| Current | Production |
|---|---|
| Synthetic CSV generator | Fivetran, Airbyte, or custom connectors per source system |
| `bq load` CLI | Orchestrated ingestion jobs with retries and alerting |
| Local Dagster dev server | Dagster+ or a scheduled VM |
| Manual dashboard refresh | Scheduled Looker Studio refresh |
| File-based catalogue | DataHub, OpenMetadata, or dbt Cloud catalogue |
| Hand-written AI context | Auto-generated from the dbt manifest |
| Single-project BigQuery | Separate dev, staging, and prod projects |
